# AIZEN AI — Security Policy & Sandbox Model

Security is a foundational design priority for **AIZEN AI**. Because AIZEN executes commands, manipulates project files, and interfaces with external language models, strict defense-in-depth protections are enforced across all layers.

---

## 1. Threat Model & Boundaries

AIZEN AI operates in user space on local developer workstations. The primary security objectives are:

1. **Prevent Unintended System Destruction**: Guard against accidental or LLM-hallucinated destructive commands (`rm -rf /`, `mkfs`, system reboots, fork bombs).
2. **Prevent Unauthorized Source Overwrites**: Ensure code edits can always be previewed, audited, and rolled back before touching disk.
3. **Protect Secrets & Credentials**: Prevent leakage of API keys, tokens, or environment credentials to log files or terminal history.
4. **Prevent Remote Prompt Injection Exploitation**: Untrusted context retrieved via RAG or Web Search must never gain arbitrary code execution capabilities without explicit user approval.

---

## 2. Command Safety Engine (`core/command_safety.py`)

All terminal commands generated by the autonomous agent or requested via `/run` undergo static analysis before execution.

### Five Safety Tiers

| Tier | Example Commands | Behavior |
| :--- | :--- | :--- |
| **`READ_ONLY`** | `ls`, `cat`, `head`, `git status`, `pwd` | Executed without prompt; strictly read-only inspection. |
| **`SAFE_BUILD`** | `npm test`, `pytest`, `cargo check`, `make test` | Builds or test runs; touches temporary or build artifacts only. |
| **`WRITE`** | `touch`, `mkdir`, `git commit`, `npm install` | Modifies project files reversibly; prompts user for single Enter confirmation. |
| **`DANGEROUS`** | `git reset --hard`, `sudo`, `kill -9`, `rm file` | High risk of data loss or privilege escalation; requires explicit typed confirmation. |
| **`BLOCKED`** | `rm -rf /`, `mkfs`, `dd if=/dev/zero`, `:(){ :\|:& };:` | **Hard blocked.** Execution is completely disallowed. |

### Blocked Command Heuristics
- Filesystem formatting commands (`mkfs`, `fdisk`, `parted`, `wipefs`, `shred`)
- System power control (`shutdown`, `reboot`, `poweroff`, `halt`, `init`)
- Recursive deletion of system roots or user home (`rm -rf /`, `rm -rf ~`, `rm -rf /*`)
- Direct device writes (`dd` with `of=/dev/...`)

## 3. Code Modification Safety (`core/diff_engine.py`)

AIZEN employs a 3-step safe code mutation workflow:

1. **Dry-Run Diff Generation**: The LLM output is parsed into a unified diff. No target files are altered.
2. **Interactive Terminal Review (`/diff`)**: The user inspects syntax-highlighted additions (green) and deletions (red).
3. **Atomic Backup & Application (`/apply`)**: Target files are backed up to `~/.myai/backups/` before writing changes.
4. **Instant Rollback (`/undo`)**: If the applied patch introduces errors, `/undo` restores original files from the checkpoint.

---

## 4. API Key & Credential Isolation

- **Environment-First Configuration**: API keys are preferentially loaded from the environment:
  ```bash
  export OMNIROUTE_API_KEY="your-secret-omniroute-key"
  ```
- **Excluded from Git**: The `.gitignore` file strictly excludes:
  - `~/.myai/` state directories
  - `*.log` output files
  - `.env` and `*.key` files
  - SQLite database files (`aizen.db`)
- **No Telemetry**: AIZEN AI does not transmit telemetry, tracking data, or usage metrics to external analytics providers. All usage statistics remain strictly local in SQLite (`~/.myai/aizen.db`).

---

## 5. Reporting Security Vulnerabilities

If you identify a security vulnerability in AIZEN AI:
1. Please do **not** open a public issue on GitHub.
2. Send a vulnerability report directly to the repository maintainers with reproduction steps and impact assessment.
3. We will acknowledge receipt within 48 hours and work with you to release a patch promptly.
